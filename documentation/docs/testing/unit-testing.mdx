The project's frontend testing is built on a foundation of Vitest, chosen for its seamless integration with the Vite development environment, along with the React Testing Library (RTL).
This combination was selected for its high performance and robust built-in mocking capabilities. RTL focuses on testing components from the user's perspective by interacting with the rendered output rather than internal implementation details.
The setup is configured to automatically generate code coverage reports, providing a clear measure of test effectiveness.

## Session API

### Generate New Session ID
- **Input / User Action**
  - Client sends `POST /create-session`
- **Expected Result**
  - Server responds with `{ sessionId: string }`
  - The new ID is unique (not already in session file)
  - Session file is updated with the new ID

---

### Validate Existing Session
- **Input / User Action**
  - Client sends `POST /validate-session` with a valid session code
- **Expected Result**
  - Server responds with `{ valid: true }`

---

### Reject Invalid Session Code
- **Input / User Action**
  - Client sends `POST /validate-session` with an invalid or non-existent code
- **Expected Result**
  - Server responds with `{ valid: false }`

---

### Handle Missing Game Code in Validation
- **Input / User Action**
  - Client sends `POST /validate-session` with missing or malformed body
- **Expected Result**
  - Server responds with `{ valid: false, error: 'Invalid game code format' }`
  - Status code is `400`

---

### Get All Sessions
- **Input / User Action**
  - Client sends `GET /sessions`
- **Expected Result**
  - Server responds with `{ sessions: string[] }`
  - Returns `[]` if file doesn't exist

---

### File Read Error Handling (GET /sessions)
- **Input / User Action**
  - File exists but is corrupted or unreadable
- **Expected Result**
  - Server responds with status `500`
  - Error is logged and message is `{ message: 'Failed to read session data' }`

---

### File Read Error Handling (POST /validate-session)
- **Input / User Action**
  - File is unreadable or JSON parsing fails
- **Expected Result**
  - Server responds with `{ valid: false }`
  - Status code is `500`

---

### Write Error Handling (POST /create-session)
- **Input / User Action**
  - Write operation fails (e.g. due to file permissions)
- **Expected Result**
  - Server responds with `{ error: 'Failed to save session ID' }`
  - Status code is `500`

# Connection Reliability Tests

Tests added while fixing backend connectivity. Server tests import `sessionAPI.js` without starting the server and use small stand-in sockets; client tests use a fake `WebSocket` the test can open and drop.

## Server: `tests/sessionCleanup.test.ts`

### Session removed after the last player leaves
- **Input / User Action**
  - The only player in a session disconnects and 30 s pass
- **Expected Result**
  - The session and its fruit timer are removed

### Session kept during the grace period
- **Input / User Action**
  - The only player disconnects and just under 30 s pass
- **Expected Result**
  - The session still exists, so the player can rejoin

### Session kept while others are connected
- **Input / User Action**
  - One of two players disconnects
- **Expected Result**
  - The session remains with one player

## Server: `tests/heartbeat.test.ts`

### Every client is pinged
- **Expected Result**
  - Each connected client receives a ping

### A client that answers stays connected
- **Input / User Action**
  - The client answers a ping with a pong
- **Expected Result**
  - It is not disconnected on the next check

### A client that does not answer is disconnected
- **Input / User Action**
  - The client does not answer a ping
- **Expected Result**
  - It is disconnected on the next check

## Server: `tests/playerJoin.test.ts`

### Hippo color kept on a second join
- **Input / User Action**
  - A player rejoins with a color, then the same connection joins again without one
- **Expected Result**
  - The player keeps their color in `USERS_LIST_UPDATE`

## Server: `tests/staleSession.test.ts`

### Messages for a deleted session are ignored
- **Input / User Action**
  - `AAC_FOOD_SELECTED` arrives for a session the server no longer has
- **Expected Result**
  - No reply and no error

### Joining a deleted session still fails clearly
- **Input / User Action**
  - `PLAYER_JOIN` for a session that does not exist
- **Expected Result**

### Messages for live sessions still work
- **Input / User Action**
  - `REQUEST_COLOR_UPDATE` for an existing session
- **Expected Result**
  - `COLOR_UPDATE` is sent

## Client: `src/contexts/WebSocketContext.test.tsx`

### Messages queued before connecting are sent in order
- **Input / User Action**
  - Two messages are sent before the socket opens
- **Expected Result**
  - Both are sent, in order, once it opens

### Movement updates are not queued
- **Input / User Action**
  - `PLAYER_MOVE` is sent while disconnected
- **Expected Result**
  - It is dropped, not sent later

### Reconnects with growing delays
- **Input / User Action**
  - The connection drops twice, then succeeds
- **Expected Result**
  - New attempts after 500 ms and then 1000 ms; `isConnected` and `isReconnecting` update

### Messages queued during a drop are sent after reconnecting
- **Expected Result**
  - A message sent while disconnected is delivered once reconnected

### No reconnecting after unmount
- **Expected Result**
  - No new connection is attempted after the provider unmounts

### Reconnect delay is capped
- **Expected Result**
  - `getReconnectDelay` returns 500, 1000, 8000, then 10000 ms at most

### Every message reaches subscribers
- **Input / User Action**
  - Several messages arrive together
- **Expected Result**
  - Each subscriber receives every message of its type, in order

### Subscribers only get their own types
- **Expected Result**
  - A `REMOVE_FOOD` subscriber is not called for `FOOD_STATE_UPDATE`

### Unsubscribing stops delivery
- **Expected Result**
  - No messages after the unsubscribe function is called

### One failing handler does not block others
- **Expected Result**
  - Other subscribers still receive the message
